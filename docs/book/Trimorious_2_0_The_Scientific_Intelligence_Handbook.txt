About this edition
This technical book documents the project’s initial design, dataset remediation, benchmark
development, foundation model selection, synthetic data engineering, QLoRA training,
reported evaluation and deployment plans. It is a publication draft based on the project
materials available at the stated date. It is not a peer-reviewed research article or a
certification of scientific or commercial fitness.

Scope and rights
The book does not distribute private benchmark content, model weights, reviewer records
or access credentials. Project names, upstream models and libraries are attributed to their
respective owners. Review the manuscript, author byline, redistribution permissions and
model/data licensing before publication. No ISBN or formal publisher has been assigned.

Evidence conventions
Recorded means a value appears in a supplied artifact. Verified here means a file or
consistency check was performed for this edition. Proposed identifies planned
architecture or illustrative code. GPU training and v2 inference were not independently
rerun for this publication. Source references [S1–S11] point to the register in Appendix B.

PROLOGUE




A model built to be checked
The central idea is not that a language model should be trusted because it
sounds scientific. It is that its answers should be measurable, traceable and
open to correction.

Trimorious began as a research-oriented language model and a set of four data
repositories. The upgrade programme asked a practical question: could a compact,
accessible model become a more useful scientific reasoning assistant without requiring an
expensive foundation-model training effort? The answer required treating data, training,
evaluation and publication as one engineering lifecycle.

The project moved from a Qwen2.5-based adapter to a Qwen3-based LoRA adapter, using
Google Colab and persistent storage. The programme first audited the existing datasets,
then designed a diagnostic benchmark, selected a new foundation, constructed synthetic
scientific candidates, screened them, and trained a controlled subset.


   The measured outcome: 610/880 correct on the D07 objective diagnostic for Trimorious 2.0, compared
   with 608/880 for its Qwen3 foundation. This is a small, uncertain improvement, not proof of superior
   scientific intelligence.


This handbook is both a technical history and a reproducibility guide. It describes the
broader Trimorious Hybrid Intelligence (THI) vision, the narrower experimental LLM that
was trained, and the steps needed to validate and release it responsibly.

How to read the book
Parts I–II describe the motivation, architecture and data work. Part III follows the
benchmark and learning pipeline. Part IV records the training and evaluation results. Part
V explains inference, publication and the hybrid roadmap. Code listings are selected
excerpts or explicitly labelled teaching adaptations, not an assertion that every example
was executed in this edition.

PART I / DESIGN




01 The original challenge
From a downloadable adapter to a research-quality scientific model.

The initial production-readiness proposal identified eight release blockers: uncertain
model identity, insufficient evaluation, unverified reasoning, incomplete model
documentation, reproducibility gaps, safety, licensing and public inference compatibility.
A public repository alone is not proof that a model is reliable, scientifically validated or
commercially redistributable.

  Risk                      Engineering response

  Model identity            Pin base revision; distinguish adapter from merged weights.

  Data quality              Normalize schemas, deduplicate, verify ground truth and provenance.

  Evaluation                Compare base and adapted models on fixed questions and scoring rules.

  Reproducibility           Record seeds, versions, hashes and checkpoint lineage.

  Safety and licensing      Assess misuse, source rights and limitations; gate publication.

  Inference                 Test actual tokenizer, template, quantization and reload.


Principles of scientific assistance
A scientific assistant should help a researcher formulate hypotheses, examine methods,
reason with equations, identify assumptions, compare evidence and communicate
uncertainty. The desired behaviour is not authoritative-sounding prose. A conclusion
should be linked to evidence or a reproducible computation; when verification is
impossible, the system should say so.

The project therefore prioritised a small model with external verification pathways over a
larger model trained on unreliable data. The initial proposal considered future 7B–8B and
14B variants, but only after the methodology was demonstrated. Training a new
foundation model from scratch was outside the immediate scope.

02 The hybrid intelligence vision
A probabilistic language model is one component of a scientific intelligence
system.

                                                  Research Studio / Scientific Lab
                                                          Future workspace



                                                   Adaptive intelligence router
                                                         Future orchestration



            Trimorious 2.0                               Specialist models                   Symbolic engines
            Trained core LLM                                   Planned                       Offline checks only


         Knowledge + RAG                                   Agentic tools                      Scientific Lab
                 Planned                                 Candidate traces only                    Planned



                                                    Verification + provenance
                                          Offline implemented; runtime integration planned




Figure 2.1 — Target THI architecture. Only the core LLM and offline dataset/benchmark verification are evidenced in
the current experiment.

The intended hybrid combines learned language capabilities with deterministic symbolic
and numerical computation, retrieval and evidence, specialist models and controlled
research agents. The router would decide whether an answer can be generated directly,
must be calculated, needs a source or requires a larger investigation.

A separate evidence layer should preserve the original source, method, observations and
limitations. This would make it possible to distinguish unverified text, source-checked
claims, computationally verified results and independently validated findings. None of
these runtime integrations should be inferred merely from an SFT dataset containing tool
traces.


   Scope decision: release the experimental Qwen3-based LLM first. THI routing, live tool execution,
   scientific RAG, simulations and the research studio are future system components.

03 Roadmap and release strategy
The original sixteen-week programme was a planning estimate, not a claim
about actual duration.

  Phase             Original plan                   Outcome in this experiment

  1–2               Audit and baseline              M1.1–M1.3.1; source audit and D07

  3–5               Restructure D01–D04; D05–D07    M1.2.1; candidate reconstruction

  6–8               Expand science, safety, tools   M1.4–M1.4.1; synthetic pilots

  9–12              SFT, DPO, GRPO                  M2.0 SFT only; DPO/GRPO skipped

  13–14             Verification and optimization   M2.3 objective evaluation reported

  15–16             Public release                  Private upload reported; public approval pending


A deliberately narrower pathway emerged as Colab GPU availability and data quality
constrained the programme. Rather than requiring all future capabilities to ship together,
the engineering decision was to focus on a reproducible core model. Preference
optimization and reinforcement learning became optional after supervised fine-tuning.

Release boundaries
The original model and datasets were to remain immutable. Derived candidates,
benchmark artifacts and the new adapter have distinct identities. The new Hugging Face
target is roime81/trimorious-research-4B-v2; the original roime81/trimorious-research-4B
remains the baseline.

The seven-stage workflow later consolidated recovery, approval, smoke testing, training,
evaluation, packaging and publication. Each stage has a different success condition.
Downloading weights is not training; passing a smoke test is not final validation; a private
upload is not a public release.

04 The four starting datasets
A record count is an inventory, not a measure of learning value.

  ID / repository suffix                           Rows             Observed schema

  D01 scientific-instructions                      3,706            messages

  D02 symbolic-trajectories                        7,784            messages

  D03 knowledge-base                               7,784            doc_id, title, source, section, text

  D04 agentic-reasoning-knowledge                  225              messages, ground_truth

  Total                                            19,499           Four different source contracts


The reconstruction bundle records exact revisions for the four repositories. D01 and D02
were conversational data, while D03 was a document-chunk knowledge base. D04 held
conversations and expected results. Treating all rows as flat question/answer pairs led to
false deduplication during the first remediation pass.

Version and naming discipline
The proposal and reconstruction use D01 for scientific instructions and D02 for symbolic
trajectories. Earlier repository documentation used these identifiers in reverse. The book
adopts the reconstruction convention and recommends explicit repository-to-ID mapping
in future manifests.

An earlier normalization run left a discrepancy of 596 records. The subsequent
reconstruction reconciled every source row, but the historical cause was not established.
Recording that uncertainty is preferable to inventing a reason for the missing data.


   D03 is retrieval material by default, not supervised fine-tuning material. Licensing and evidence
   extraction must be handled before making its contents distributable or treating passages as training
   answers.

05 Reconstruction and quarantine
The first lesson: duplication can hide behind a large dataset.

  Source         Disposition                                                    Count

  D01            Distinct rebuilt math candidates                               3

  D01            Repeated templates collapsed                                   2,003

  D01            Unsupported prompts quarantined                                1,700

  D02            Distinct rebuilt math candidates                               4

  D02            Repeated templates collapsed                                   7,780

  D03            Retrieval-only; license review                                 7,784

  D04            Distinct replay candidates                                     12

  D04            Repeated templates collapsed                                   213


The corrected M1.2.1 processing accounted for 19,499 rows. It did not claim that the 19
rebuilt symbolic/replay candidates were training-ready. Rather, it preserved usable
examples for review, collapsed repeated patterns and quarantined records whose source
prompts did not support the answers.

Four recurring symbolic functions accounted for almost all D02 entries. This discovery
changed the development strategy: the project needed new verified task mechanisms, not
just additional copies of examples.

The disposition ledger
Every record receives a source identity, schema and normalization status, a reason for
inclusion or exclusion, and an approval state. A quarantine is evidence of work done, not a
deletion of inconvenient results. This allows later reviewers to reconstruct exactly how the
training corpus was derived.

06 The D01–D10 data strategy
A portfolio of datasets designed around distinct capabilities.

  ID            Purpose                               Original planning target

  D01           Scientific instructions               50k–100k examples

  D02           Symbolic trajectories                 100k–250k trajectories

  D03           Scientific knowledge/evidence         50k–100k claims

  D04           Agentic reasoning                     20k–50k trajectories

  D05           Mathematical verification             50k examples

  D06           Scientific preferences                30k–50k pairs

  D09           Safety and reliability                15k–30k examples

  D10           Scientific environments               100–500 environments


These are aspirational quantities from the initial proposal, not the size of the present

D06 would support preference learning with verified chosen/rejected pairs. D08 would
support Bahasa Malaysia and other languages, with equivalent scientific terminology and
answers. D09 would test and teach reliability, including uncertainty and citation integrity.
D10 would define states, observations, allowed actions, termination and rewards for
scientific tasks. D07 remains held out from all learning.

07 Structured scientific data
Represent the question, the evidence and the result as distinct objects.

The original design called for structured symbolic trajectories with problem identity,
domain, difficulty, explicit mathematical operations, final answer, verification engine and
provenance. Agentic records were to contain goals, planned actions, actual tool calls,
observations and recovery decisions. This format is more expressive than a plain
conversational answer.


   {
       "trajectory_id": "DEMO-SYM-001",
       "domain": "calculus",
       "problem": "Differentiate x**2 * sin(2*x)",
       "steps": ["product rule", "chain rule"],
       "final_answer": "2*x*sin(2*x)+2*x**2*cos(2*x)",
       "verification": {"engine": "sympy", "status": "review"},
       "source": "illustrative synthetic example"
   }


Listing 7.1 — Teaching example adapted from the initial proposal; not a D07 benchmark item.


Evidence graph design
A future D03 evidence repository would maintain papers, claims, equations, experiments
and findings separately. A claim should identify its source location, DOI where applicable,
units, assumptions, extraction confidence and review status. Relations such as supports,
contradicts, tests, derived_from and reproduces preserve the reasoning context.

A generated interpretation must never overwrite its evidence passage. Store raw sources,
extracted chunks, normalized claims and derived examples as separately versioned assets.
Verify rights at each transformation and preserve attribution.

08 The first verified corpus
M1.4: a small generator designed to fail visibly.

  Capability                         Candidates         Capability                          Candidates

  Mathematics                        200                Scientific reasoning                150

  Agentic tools                      150                Statistics                          100

  Methodology                        100                Verification                        100

  Experiment design                  60                 Literature synthesis                50

  Academic articulation              50                 Ethics/reliability                  40


The initial generator created 1,000 candidates from 63 templates, with 795 development
and 205 validation examples. Six hundred numerical checks passed, including 150 actual
single-tool replays; 400 narrative examples still required rubric review. No examples were
approved for training at this stage.

The agentic tasks used bounded computational tools such as weighted averages,
trapezoidal integration, regression slope and numerical roots. The generator recorded
inputs, observations, verification and replay outcomes. This is evidence of executed
scientific functions, not a demonstration that a language model autonomously chose them.

Screening against the frozen diagnostic
The question-level D07 check reported zero flags at character similarity 0.78 and word
similarity 0.72. The maximum observed similarities were 0.4134 and 0.5328. This
establishes only the absence of flags under those lexical rules. It does not establish
semantic independence or absence of pretraining contamination.


   M1.4 remains a candidate dataset. The final training experiment did not simply concatenate its 1,000
   records with the subsequent 5,000.

10 Multi-tool execution and teachers
Tool traces are useful training candidates only when actions and
observations are independently checked.

M1.4.1 expanded from single-tool tasks to 750 workflows with dependent steps. Its report
records 1,500 successful execution steps, 150 deliberately rejected calls and 1,650 passing
replay checks. These traces belong to bounded generator-owned functions, not
unrestricted execution of model-produced code.


   # Illustrative bounded tool workflow
   readings = [12, 18, 25, 37]
   total = sum(readings)
   try:
        rate = total / 0
   except ZeroDivisionError:
        corrected_duration = 5
        rate = total / corrected_duration
   assert rate == 18.4


Listing 10.1 — Teaching example of error recovery, not a recorded benchmark trace.


Teacher orchestration
Qwen3 and Phi-4-mini were configured as candidate teachers, not guaranteed stronger
models. The teacher saw the original prompt and permitted evidence, but not reference
answers or D07. Each proposal was stored separately, with numerical checking and
narrative review. SQLite checkpoints were keyed by corpus, model revision, prompt
configuration and runtime.

The Colab session later reported 98 Qwen3 proposals and zero Phi proposals, with
database integrity OK. Remaining teacher inference was deliberately skipped. The final
SFT audit states no teacher text and no tool traces were included in training. These two
experiments therefore cannot be credited with the measured adapter improvement.

11 Design of the TSIB benchmark
Trimorious Scientific Intelligence Benchmark (D07): a diagnostic, not a
universal intelligence score.

  Task family                               Cases        Evaluation type

  Mathematical reasoning                    200          Objective

  Scientific reasoning                      150          Objective

  Research methodology                      120          Objective

  Statistical reasoning                     120          Objective

  Experimental design                       100          Objective

  Scientific verification                   100          Objective

  Literature synthesis                      80           Rubric

  Agentic tool use                          60           Objective

  Academic articulation                     40           Rubric

  Ethics/reliability                        30           Objective

  Total                                     1,000        880 objective + 120 rubric


The benchmark comprised 50 synthetic templates, of which 44 contributed objective
questions. A separate answer key allowed controlled scoring. The hardened scorer
distinguished correct content from strict protocol compliance and evaluated tool-task
success independently.

The gold keys and question files remain private and should never appear in a public model
card, training dataset or teacher prompt. The benchmark is now a known diagnostic
because later generators were designed with knowledge of its structure. Its repeated
templates and nonrandom selection constrain inference beyond the test itself.

12 Scoring and paired comparisons
A stronger scorer must not turn evaluation into a moving target.

M1.3.1 introduced flexible numeric parsing, independent answer-key auditing and
separate content/protocol measures. The objective evaluation checked 880 keys; 120 rubric
items required expert review. The same hardened rules were reused in the subsequent
foundation selection.


   # Illustrative exact paired McNemar computation
   from scipy.stats import binomtest
   wins = 6      # candidate right, base wrong
   losses = 4    # base right, candidate wrong
   p = binomtest(min(wins, losses), wins + losses,
                 p=0.5, alternative="two-sided").pvalue
   # 0.75390625 for the reported v2 comparison


Listing 12.1 — Calculation of the reported paired p-value; does not reproduce raw evaluation responses.

For a paired test, the relevant information is discordant outcomes: how many tasks one
model gets right when the other gets wrong. The paired difference equals (wins minus
losses) divided by the total number of objective tasks. McNemar’s exact test uses the
discordant count under a symmetric null.

Repeated questions from the same template are correlated. A template-level bootstrap
resamples template groups, rather than treating every row as independent. This gives a
descriptive interval that reflects some dependence, but does not make the synthetic
benchmark a random sample of real science.


   Keep checkpoint selection on a development evaluation set. Use a separate independently authored
   confirmation test only after the final adapter is frozen.

13 What the original model taught us
The first adapter did not outperform its base on the frozen objective
benchmark.

  Model / metric                              Qwen2.5 base                   Trimorious v1

  Objective correct                           449 / 880                      403 / 880

  Accuracy                                    51.02%                         45.80%

  Strict protocol                             73.6%                          36.7%

  Agentic objective                           40 / 60                        7 / 60


The paired evaluation reported 96 questions where only the base was correct and 50
where only the adapter was correct. The difference was -5.23 percentage points. The
ordinary exact p-value was approximately 0.000175; the template-cluster interval was
-13.72 to +1.90 percentage points.

The results were enough to motivate a redesign, but not enough to establish catastrophic
forgetting as the causal mechanism. The historical training base revision was not verified,
the benchmark was synthetic, and the dataset audit exposed repeated patterns. A future
ablation would need to isolate the effects of data, training hyperparameters, evaluation
protocol and model identity.

The engineering conclusion
Do not continue fine-tuning the old adapter by default. Rebuild the source data contracts,
establish a clean comparison baseline and evaluate multiple candidate foundations.
Preserve the original model as a historical reference rather than overwriting it.


   The old repository name includes “4B”, but its recorded base is Qwen2.5-3B-Instruct-bnb-4bit. The name
   should not be mistaken for a verified parameter count.

15 Approval, recovery and the seven gates
The final development path was built to survive interrupted Colab sessions.

   01        Recover

   02        Approve

   03        Smoke

   04        Train

   05        Evaluate

   06        Package

   07        Publish

Figure 15.1 — Seven-stage release workflow; each stage is gated by persistent evidence.

The candidate corpus was recovered from its ZIP archive and compared with the original
corpus fingerprint. A previous export failed when the active records variable contained
850 rows rather than 5,000 and lacked fingerprints. The integrity assertion correctly
stopped export. Recovery reloaded the original data and preserved SQLite teacher
proposals.

A separate failure occurred at Qwen3 loading: the T4 process occupied 14.31 GiB of 14.56
GiB. Only 257.81 MiB was free while the next allocation requested 742 MiB. The project
moved to a clean runtime, 4-bit quantization, separate GPU worker processes and
persistent checkpoints. This reduced the risk of models left in memory from previous
stages.

The combined release notebook separates preparation, approval, smoke testing, full
training, evaluation, packaging and publication. “Run all” is a controller, not permission to
bypass scientific review or publish a model automatically.

On restart, mount Drive and verify the archived corpus and approved dataset hashes
before loading a model. The active training directory is keyed by the complete training
configuration. A changed dataset, revision, software environment or hyperparameter set
must not silently reuse an unrelated checkpoint.

Google Colab’s temporary /content directory is ephemeral. Preserve notebook code,
approved data, benchmark files, training checkpoints and review evidence on persistent

18 Integrity and numerical verification
A cryptographic digest detects unexpected changes; it does not certify
correctness.


   import json, hashlib, zipfile
   from pathlib import Path

   def canon(x):
       return json.dumps(x, ensure_ascii=False,
                         sort_keys=True, separators=(',', ':'),
                         allow_nan=False)

   def sha(b):
       data = b if isinstance(b, bytes) else canon(b).encode()
       return hashlib.sha256(data).hexdigest()

   def archive_check(z):
       ns = z.namelist()
       assert len(ns) == len(set(ns)) and z.testzip() is None
       m = json.loads(z.read('archive_manifest.json'))
       assert set(m) == set(ns) - {'archive_manifest.json'}
       assert all(sha(z.read(k)) == v for k, v in m.items())
       return m

LoRA represents an update to a frozen weight matrix W with a low-rank product.
Conceptually, W′ = W + (alpha/r) BA. The matrices A and B are trainable, while the original
model remains the required foundation at inference. QLoRA stores the base in a low-bit
representation and computes in a supported higher precision.

With 288 training rows, batch size one and gradient accumulation of 16, the recorded
one-epoch run corresponds to 18 optimizer steps. This is a controlled pilot. The short run
and limited template variety constrain what can be concluded about generalisation.

EPILOGUE




The discipline of verification
The strongest result is a process that makes its own limitations visible.

Trimorious 2.0 began with an ambitious scientific intelligence concept. The work exposed
the limitations of the original training corpus, produced a frozen diagnostic, compared
candidate foundations, generated verified synthetic data, survived memory and
state-management failures, and completed an experimental QLoRA run.

The evidence supports an upgraded, trained Qwen3-based adapter and a structured
engineering workflow. It does not establish a large reasoning gain over the new base. The
original target of a full hybrid research assistant remains an architecture programme:
evidence retrieval, adaptive routing, live symbolic verification and scientific

The next iteration should prioritize genuine mathematical task diversity, reviewed
